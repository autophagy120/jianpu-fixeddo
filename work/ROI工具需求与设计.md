# ROI 纠错工具 · 完整需求与设计

> 需求方说明原文要点逐条对应。这是待实现清单，按优先级排。

## A. 可点击的「橙色框」= 检测到但没输出数字的音符

**问题**：几何侧切出了槽位（橙框），但 OCR 没给数字 → 目前只能"加强识别"或"强制插入"。

**目标**：橙框本身可点，点开就是数字 + 五八度按钮面板，选完即成为正式音符。

**实现**：
- 服务端 `/notes` 增加 `paired:false` 的槽位（来源 `page._slots` 里不在 `pairs` 中的）
- 前端把它们画成橙色框；命中判定纳入候选
- 新接口 `POST /assign {slot_id, digit, oct}` → 把该孤儿槽位并入 `pairs`

## B. 图片导入与批量导入，可选原调/转调

**目标**：不再把文件名写死在代码里。

**实现**：
- 启动时不需要 `--song`，改为网页里上传，或选择一个目录做批量
- 每张图记录：`原调`（12 个升号写法：C C# D D# E F F# G G# A A# B）、`目标调`（默认 C）
- 批量模式：列表显示每首相态（待处理/转换中/完成/失败），可单独打开某一首进 ROI 纠错
- 服务端 `POST /open {path|upload}` 切当前页；`GET /list` 返回批次状态

## C. 主字号 / 辅助字号（解决字号乱跳）

**问题**：几何按每个槽位自己的高度定字号，同一行内会一大一小。

**目标**：
- 每行有**一个主字号**（行内中位字高），默认所有音都按它渲染
- **行内所有音共用同一条基线**（需求方补充）：以前每个音按自己的槽位框底边对齐，
  检测框深浅不一，图上就是"一个上一个下"——这是渲染问题，不是原谱问题
- 少数音可被标记为**辅助字号**（和声行、装饰音等小字），字号按比例，**基线不动**
- 一切统一，除非明确标出例外（= 标成辅助字号）

**实现**：
- 数据模型：`pairs[i].size_class ∈ {main, aux}`
- 渲染：`gh = 行中位字高`（用主字号音算，夹在 0.80–1.25 × 页中位）或 `gh × aux_ratio`
  （`aux_ratio` 默认 0.72）；基线 `base = 行内中位框底`，`oy = base - bbox[3]`
- 八度点跟着**画出来的字形**走（`oy+bbox[1]` / `oy+bbox[3]`），不跟原槽位框
- UI：选中音符 → 「设为主字号 / 设为辅助字号」两个按钮；行级「统一为本行主字号」按钮
- 服务端 `POST /size {ids[], class}` / `POST /size_row {row, class}`
- 实测（BadApple）：改前各行框底极差 6–22 px，改后**行内基线极差 0 px、字高极差 0 px**

## D. 临时转调段（`转1=G` 之类）

**理解**：谱面中途临时换调，例如某行写着 `转1=G`。该处之后到下一个转调点之前，音符要按**新调**解释。

**关键要求（需求方明确）**：
1. OCR 修正阶段**不做任何改变** —— 识别到的数字保持原样
2. 仅在后台**打 TAG**（标记某个位置发生转调、目标调是什么）
3. 转调阶段：在 TAG 之后的部分，按新调算绝对音高，再统一落到 C 或 C# 记谱
4. 可能**存在多次**转调 → 要支持标记多个点

**数据模型**（按需求方确认：**不能按行号**，因为可能从一行的半路开始转）：

```json
"key_changes": [
  {"x": 812.0, "y": 1466.0, "key": "G"},   // 从该位置（含其后的音）开始 1=G
  {"x": 320.0, "y": 2205.0, "key": "D"}
]
```

锚点是一个**图上的点**，不是行号。语义：

- 阅读顺序定义：先按 y 排（同一视觉行归一行），行内按 x 排
- `segment_key(note)` = 所有"阅读顺序在该 note 之前"的锚点中，最后一个的调
- 一个锚点落在某行中间时，**该行中 x ≥ 锚点 x 的音**才切调，左边的音仍用旧调
  —— 这正是"从半路开始转"的场景
- 支持任意多个锚点，按阅读顺序依次覆盖

**为什么用点而不用行号**（需求方指出）：转调可能从一行中间开始，行号粒度太粗。

**实现要点**：
- 转调时按锚点切段：`key_of(note) -> 调名`
- 每个音的绝对音高 = `note_to_abs(deg, acc, oct, key_of(note))`
- 再 `abs_to_movable(..., 目标调 C/C#)`，八度保持绝对（`octave_mode='absolute'`）
- 锚点存的是原始坐标，插入/修改音符后自动重算，不需要维护索引

**UI**：
- 点「标记转调」→ 鼠标变成十字 → **在谱面上点一下**（可以点在一行的任意位置，不必对齐音符）
- 立即弹 12 个调名按钮（`C C# D D# E F F# G G# A A# B`）→ 选完生成 TAG
- 图上画一条**竖直虚线 + 小标签**标出分界位置（`1=G`），一眼能看到转调点
- 右侧列表：`(x=812, y=1466) → 1=G`，可删除、可改调
- 识别数据完全不动，仅影响转调计算

## G. 乐谱库（B-2/B-3/B-4 实现说明）
- 入口：`http://127.0.0.1:<port>/lib`；纠错页就是 `/`，左上角「← 乐谱库」返回。
- 库文件：项目根目录 `library.json`（一条记录 = 一页），字段
  `id / song / image / title / ocr_txt / key / target / status / out / notes / uncovered`。
- `status`：`new` 仅登记 → `ocr` 有 OCR 文本 → `done` 已出红字图 → `error`。
- 导入：填目录（递归扫描）或单个图片路径；自动排除 `(原调…_转调C)` 对照图；
  按子目录名当歌名。**导入不烧 GPU**，只登记。
- 打开/处理/批量都在后台线程跑（`/api/job` 轮询 + 底部进度条），
  因为一页对齐要 10–30 秒、OCR 更久，不能卡请求。
- 处理流程与 `jp\batch.py` 完全一致，OCR 文本缓存在 `out\batch\_ocr\<歌>__<页>.txt`，
  重跑不再算；出图写 `out\batch\<歌>\<页>_fixed.jpg`。
- AI 只做「从 OCR 文字猜 曲名/歌手/调号」：`jp\llm.py`，OpenAI 兼容接口，
  配置 `work\llm.json`（复制 `work\llm.json.example`）；**图片一个字节都不发**。

## H. 多原调 / 去重 / AI 分类（2026-11 追加）

**多原调（一个谱面可能多次转调）**
- `jp\library.py: detect_keys(txt)` 扫 OCR 文本里**所有** `1=X`（`#F`、`bA`、`F#` 都认），
  返回 `[{key, line}]`；相邻重复（谱头常写两遍）只记一次。
- 库里每条记录存 `keys`（全部调）、`key`（当前用哪个）、`multi`（是否按中途转调渲染）。
- 库页面：原调列显示成小圆球（点一下即设为当前原调）；勾「中途转调」后，
  批量出图按 `行号/总行数 × 页高` 切段，逐音用自己的调算绝对音高（`_segments_for`）。
- 打开纠错页时，检测到的中途转调会**自动种成紫色锚点**（可拖可删），与批量语义一致。

**不重复处理已转调的图**
- 判据：接近纯红像素 `(R>140, G<70, B<70)` 占墨迹比 > 0.06 且绝对数 > 3000。
  语料标定：原始页最高 0.28（那张其实是转调图）、转调输出最低 0.17 → 0 漏判。
- 文件名带 `(原调…)` 的**直接不入库**；其余在导入时算一次，标 `dup`，批量自动跳过。
- 顶栏「检查已转调」可全量复检（111 张约 18 秒）。命中 1 张：`世末歌者CD (1).jpg`
  （文件名没带 `(原调` 但内容就是转调输出）。

**AI 分类未命名页**
- `/api/classify`：只挑「没有标题 + 已有 OCR 文本」的页，把文本发给 LLM 猜歌名/调号；
  未配置 key 时直接报错，不静默跳过。
- **手动拖页序**：表格左侧 ✥ 拖到同歌的某一行前面，落盘 `order`（`/api/reorder`），
  页码识别不了也能手动排。

**顺带修正一个旧错误**：Bad Apple 的原调谱头 OCR 是 `1 = #F`（Db 侧记谱），
旧代码里硬编码成 `G`，半音之差。现在原调一律从 OCR 文本读，SONGS 里的默认值也改成 `F#`。

## I. 导入方式与打开缓存（2026-11 追加）

**导入：浏览器选择器 + 路径登记，两种都行**
- 「选择文件夹导入」/「选择图片导入」：`<input type=file webkitdirectory>` / `multiple`，
  文件**上传并复制**进 `library\<id>\page.jpg`（歌名取相对路径的文件夹名）。
  前端每 8 个文件一批，避免一次几十 MB 卡住。
- 「按路径登记」：粘贴本机目录/单文件，只登记不复制（语料批量导入用，快）；
  之后随时点「复制进本地库」把外部文件搬进 `library\`。
- 上传去重：id = 内容哈希 + 文件名，同一张图重复导入只算「重复」，不会多一条。

**导入源管理**
- 每次导入（上传或路径）都记一条 `sources`：名称/方式/备注/时间；可删除。
  删除**只删记录**，已导入的页不动。
- 修过一个 bug：以前 `_save_all` 整体覆盖 `library.json`，把 `sources` 冲掉了；
  现在只覆盖 `items`，其余字段保留。

**打开缓存（关键提速）**
- `library\<id>\cache.pkl` 存 `page`（几何）+ `pairs`（识别结果）+ 手工改动
  （`key_changes` / `target_pc` / `erase_boxes`）+ 来源图指纹。
- 指纹 = **大小 + 前 1MB 内容哈希**（不用 mtime）：归档/换目录不会让缓存失效，
  内容真变了才作废，且旧格式缓存按大小兼容读入。
- 实测（三月雨，441 音）：**第一次 26.9s → 之后 1.3s（约 20×）**，缓存 25.8MB。
- 纠错页工具栏「保存到库」把当前状态（含手工改的音、转调点、字号、目标调）写回缓存，
  下次打开就是改好的样子。

## J. 图片格式支持（2026-11 追加）

- 支持 `jpg/jpeg/png/gif/bmp/webp/tif/tiff/avif`（heic 需 `pillow-heif`，失败会**列出文件名和原因**，不静默丢）。
- 解码策略：`cv2` 优先，解不了的走 `Pillow`。
  - 能原样存的（gif/webp/tif…）按原格式存；
  - `avif`（cv2 无解码器、Pillow 12 可读）**自动转成 jpg q95** 再入库，下游 `core.load_gray` 才能读。
- 路径登记时若遇到 `avif/heic/heif`，同样先转码进库再用。
- 实测：gif 直接入库可跑 `core.load_gray`；avif 转码后 `load_gray` 正常（742×1003）。
- 导入框里**不再放原调输入**（容易误解），原调统一在曲目表里逐页调（支持多调）。

## K. 实时更新 + 自动按份分组（2026-11 追加）

**更新（扫新文件）**
- 顶栏「更新（扫新文件）」按钮 → `POST /api/rescan`：把所有「按路径登记」的目录重新 walk 一遍，
  新文件只登记、不烧 GPU。实测 142 个文件 **1.9s**，重复扫描幂等。
- **打开页面时自动扫一次**（`refresh().then(rescan(true))`），有新增会提示并刷新列表。
- 历史导入的目录不用重新导入：`ensure_sources_from_origins()` 会从条目的 `origin` 反推目录
  并登记成导入源。
- **导入源只列顶层目录**（需求方：要读子文件夹，但别把子文件夹都列出来）：
  `collapse_sources()` 同一盘符内取**共同前缀**（至少 2 层，不会退化成盘符根），
  互相包含的只留最上层；扫描本身是递归的，子目录照样覆盖。
  实测 51 个歌曲目录 → 折叠成 1 个根目录 `E:\…\转调简谱`，源清单只剩 2 条
  （1 个路径根 + 1 个上传源），`ensure_sources_from_origins()` 再跑返回 0（幂等，不会又长出来）。
- 按路径导入时服务端也会自动登记 source；上传导入记成 `kind=upload`（无路径可扫）。

**自动按份分组**（判断哪几页属于同一份简谱）
- 顶栏「按份自动分组」→ `POST /api/group_auto`（后台任务，实测 141 页 0.5s）。
- 判据从强到弱：
  1. **同一目录**（子文件夹名）→ 同一份；
  2. **歌词/谱面文字相似**：字符二元组 Jaccard ≥ 0.25 → 同一份，即使时间隔得很远；
  3. 同目录且没文字时看**文件时间间隔**：取相邻间隔里"跳得最开"的一档
     （相邻间隔比值 ≥ 1.8），阈值取两簇的几何中点。
     你给的例子（谱内 5s、谱间 20s）阈值≈10s，正好切在谱与谱之间；
     若所有间隔都一样大（例如每页都隔 10 分钟）则不切，避免乱拆；
  4. 缺时间的页不单独断开。
- 分完写回 `group / group_title / group_pos / group_n`，列表按组显示"共 N 页"。
- 合成用例 4/4 通过：歌词相同+大间隔→2 份；无歌词 5s/20s→2 份；
  无歌词全 4s→1 份；歌词不同+大间隔→2 份。
- 真实库：141 页 → **51 份**，与语料里 51 个歌曲目录一致。
- 局限（如实说明）：**上传导入没有真实"下载时间"**，只能用到达时间近似，
  所以对上传的散图，分组更依赖歌词相似度；有文字时优先看文字。

## L. 两栏工作区（2026-11 追加）

- **左栏 = 已分类**：每份谱一张卡片，**默认折叠**（只显示名字 + N 页），点标题展开/折叠；
  折叠状态存 `groups[gid].collapsed`（`/api/group_toggle`）。
- **右栏 = 未分类**：页面卡片。
- **手动分类**：右栏卡片 / 左栏组内行都能拖动；
  - 拖到左栏某份谱上 → 移入该谱（`/api/move {ids, group}`，组尾追加，自动修正 `group_n`）；
  - 拖到右栏 → 退回未分类。
- **右键菜单**：
  - 左栏空白处 → 「新建一份谱…」(`/api/group_new`)；
  - 组标题 → 重命名 / 全部打开 / 删除（删除后页退回未分类，`/api/group_del`）；
  - 页面卡片 → 打开纠错 / 归到别的谱 / 移出到未分类。
  - 也可用卡片上的「归类…」输入谱名（不存在会自动新建）。
- **预览（左右两栏都有）**：
  - 卡片左侧有 46–74px 小缩略图（`/api/thumb`，宽 300，懒加载）；
  - **鼠标悬停**弹出放大图 `/api/preview`（宽 1100，q86，约 240KB，生成 0.1s、之后命中缓存 0.01s），
    跟随鼠标定位、超出屏幕自动翻边，**移开即消失**。
  - 这样不用点进去渲染就能认出是哪一页，排序/归类才有意义。
- 数据模型：新增 `groups`（`{id,name,created,collapsed}`），页面条目加
  `group / group_title / group_pos / group_n`；`auto_group` 会顺带创建 groups 记录。
- 实测：141 页自动分成 51 份；新建谱→移入→移出→改名→折叠→删组 全链路通过；
  缩略图 32KB、预览 241KB。

## M. 垃圾箱 / 重复检测 / 设置菜单（2026-11 追加）

## S. OCR 并行调度（CPU+GPU，2026-11）

需求：别浪费算力，GPU 和 CPU 都要喂满，并且能选串行还是并行。

- `xiaomi_ocr.ocr_batch()` 改成**任务队列 + 多工人抢任务**：
  - `serial`：1 GPU
  - `cpu_gpu`：1 GPU + 1 CPU（CPU 用 `llama` 纯 CPU 二进制，`-t 6`）
  - `gpu2`：2 GPU
  - `max`（默认）：**1 GPU + 3 CPU**（`-t 3`）
  - 环境变量可覆盖：`OCR_GPU_WORKERS / OCR_CPU_WORKERS / OCR_CPU_THREADS`
- **实测结论（GTX1650 4G）**：
  | 配置 | 显存 | 单页耗时 | 结论 |
  |---|---|---|---|
  | 串行 1 GPU | ~0.95G | 37–177s（看页密度） | 基准 |
  | **3 GPU + 3 CPU** | **3.7G/4G** | **600–750s** | ❌ 超量分配走共享内存，反而慢 5–10 倍 |
  | **1 GPU + 3 CPU（max）** | ~1G | **14 页 536s = 38.3s/页** | ✅ 采用 |
  GPU 独占显存才不会塌；CPU 每页约 9 分钟（很慢），只贡献约 10% 吞吐，
  但对大页/密集页能补位，且不影响 GPU。
- **健壮性**：
  - 结果**增量落盘**（`on_result` 回调），中途杀掉不丢已完成的页；
  - 每张图的临时文件名加 pid+线程号 —— 并行时两页同尺寸会撞同一临时文件
    （这和 OCR 缓存撞名是同一类坑）；
  - GPU OOM 自动退回 CPU 重试该页。
- UI：设置 → 「OCR 方式：串行 / CPU+GPU / 双 GPU / 最大调度」，默认最大调度。

**跑完的结果**：191/193 页有 OCR 文本；2 页 OCR 退化（连续两次输出重复垃圾，
`trim_degenerate` 后为空，多半不是谱面）已标 error。

**collision 修复后的复核**：`保存简谱` 那 53 页重新 OCR + 联网识别后，
标题终于**分散**了：纯蓝 3 / 越冰船 3 / 风之子 3 / 梦语 3 / 一人行者 2 / 聘书 2 /
流光 2 / 白鸟过河滩 2 / 啥啊 2 …（之前是 19 页同一个名字）。

## R. OCR 缓存撞名 BUG（2026-11，用户抓出来的）

- **症状**：19 页都被标成「光与影的对白」，查下去发现这 19 页读的是**同一个 OCR 文本文件**
  `out\batch\_ocr\保存简谱__page.txt`（文本哈希完全一致 = 同一个文件）。
- **根因**：OCR 缓存路径按「歌名__文件名」生成。用户那批是 `.avif`，入库时被转码成
  `library\<id>\page.jpg`，basename 全变成 `page` → 缓存路径全撞成同一个文件，
  **后一页的 OCR 覆盖前一页**，于是十几页读到了同一份歌词；AI 再基于这份错文本去搜，
  自然全都得到同一个歌名。
- **修复**：
  - OCR 文本改为**按条目 id** 存放：`library\<id>\ocr.txt`（`ocr_path_for_id`）；
    `ocr_path_for(song, image)` 在不带 id 时也用图片路径哈希保证唯一。
  - 迁移脚本把 165 页文本搬到新位置；**撞名的 24 页**（都是转码后的 avif 页）标记为需要重新 OCR，
    并**清掉那 19 条错标题**。迁移后重复的 OCR 路径 = 0。
  - 用本地 Xiaomi-OCR 重跑这 24 页（约 3 分钟/页），完成后只对这批重新跑联网分类。
- 顺带体检：170 页有文本、**149 种不同文本**；重复的 2 页一组都是同一页的 png/jpg 两份，
  说明管线本身没问题，问题就出在缓存路径上。

## Q. 分份阈值改成「均值+标准差」，并改用 AI 标题（2026-11 修正）

**用户反馈**：所有页被分到「越冰船 / 光与影的对白」两个大组里。原因有两层：
1. 时间切分用了"两簇几何中点 / 3×中位数"这类绝对规则，而那个文件夹的间隔里有
   0/1 秒的连拍、也有 2853 秒的长间隔，σ 极大 → 只切出 2 段；
2. `aggregate_group_titles` 又把每段按"出现最多的 AI 标题"改名 → 整段被命名成
   「光与影的对白」等，看起来就像"全都分到这两首去了"。

**修正**
- 时间阈值改为需求方要求的 **均值 + 1.5σ**（只用正间隔，至少 10s）：
  `thr = max(10, mu + 1.5*sd)`。
- 新增 `auto_group_by_title()`：**优先按 AI 标题聚类**，比时间可靠得多。
  - 规范化标题（NFKC、去括号补充、去标点空白）后，二元组 Jaccard ≥ 0.55 或互相包含 → 同份；
  - 没标题的页：同目录且与某簇时间间隔 ≤ 1.5×阈值 → 并入，否则单开一组（目录名+序号）；
  - 组名 `name_locked=True`，之后「用 AI 标题汇总谱名」不会覆盖。
- `aggregate_group_titles()` 现在尊重 `name_locked`，不再把目录名/手工名盖掉。
- 设置菜单新增 **「按 AI 标题重新分份（推荐）」**；原来的时间分份保留。

**结果**：`保存简谱` 那 53 页从 2 份变成 **16 份**（光与影的对白 24 / 越冰船 4 /

- 配置落地：`work\llm.json`（**key 只在配置文件里，不进源码**；接口只回 `key_mask=sk-…49e9`）。
  默认 `base=https://api.deepseek.com`、`model=deepseek-flash`。

## T. 转调锚点"插到后面去"的修复（2026-11）

- **现象**：在一行的**行首**点「标记转调」，结果转调从下一行才生效，看起来像插到了后面。
- **原因**：切段时直接拿点击的 y 和每个音的中心比（容差 ±0.5 字高）。行首点击往往落在
  数字上方/下方（谱线、歌词、空隙），只要偏差超过半个字高，这一行就整个被判成
  "不在锚点之后"，于是新调从**下一行**才开始。
- **修复**（`State._anchor`）：
  1. 先把点击位置**吸附到最近的一行**（1.5 个字高内取最近行中心），
     这样点在行首偏上/偏下 20–40 px 都还算这一行；
  2. 如果点击 x 在该行最左音符左边（行首或更左），把锚点 x 设到行首左侧一点，
     保证**整行**都进新调；
  3. 图上紫色标记线也用吸附后的位置画，和实际生效位置一致。
- 单测 8 条全过：行首（y 正中 / 偏上 20px / 偏下 25px / 偏下 40px）→ 整行起转；
  行中点击只影响右侧；第二行行首、两行之间、行末点击都符合预期。

## U. 修正记录（自学习数据）2026-11

目标：把人的每次修正**带坐标和谱面信息**记下来，后面能训模型，也能拿来分析
"为什么这类地方总错"。

**记什么**（`jp/edits.py`，事件 + 样本两层）

事件（`work/train/events.jsonl`、`library/<id>/edits.jsonl`）：
`edit / assign / insert / delete / move / size / keychange_add / target / strength / undo`，
每条带 `seq`（撤销据此丢弃样本）和 `ctx`。

样本（`work/train/patches/*.npy` 32×32 + `index.jsonl`）：
标签 = 数字 `0-7` / `reject`（不是音符）/ `blank`（擦掉的空白）。

**ctx 谱面与坐标**（每个样本都带）：

| 字段 | 含义 |
|---|---|
| `w,h,scale,med_h` | 原图尺寸、版面缩放、字高中位（坐标系基准） |
| `key,target,strength,pipe,img` | 当时调号 / 目标调 / 识别强度 / 算法版本 / 文件名 |
| `box,pw,ph` | 字形框（原图像素）与宽高 |
| `row,row_n,row_base` | 行号、该行音符数、行基线 |
| `left,right,dx_left,dx_right` | 左右邻音的框与中心距（**对齐错位的核心信号**） |

**move_note**：`Alt + 拖动` 音符微调位置；记 `box_old → box_new`、`dx,dy`，
既是对齐偏移的回归样本，也是人工位置标注。移动后按新坐标自动重选该音。

**撤销**：`undo` 事件记 `seq_from/seq_to`，汇总时被撤销的样本自动丢弃。

**用法**：`python work\harvest_edits.py --train`（样本够 40 条才真训）。
