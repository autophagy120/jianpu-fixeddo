## 参考项目预处理：接入结果（回应"为啥不修正管线"）

之前的说法不准确。正确做法不是让对方迁就我的约定，而是**让管线吃下它的输出**：

- `jp/preproc.py`：`to_uint8_ink_dark()` 统一 dtype（0–1 float → 0–255）和极性（亮字暗底 → 暗字亮底）。
  实测接入后图像结构与我原来的输入一致：墨量 10.3%、组件 1396 个、行带 34 条 —— **极性/量纲问题已解决**。
- `--preproc off|relight|deskew|both` 已接入 `jp/run.py`；纠偏角度会同步应用到彩图，保证重绘坐标一致。

**但实测结论是：这一页上 relight 是负作用。** 三月雨是数字图（不是光照不均的扫描件），
双伽马拉伸会在字周围产生光晕，把**行间空隙填上** → 行带合并（music+lyrics 黏成一条）→
行内字高离散度 cv 从 ~0.1 涨到 0.29–0.76，整页判不出谱行。所以默认 `off`，留给真正的扫描件用。

顺带修掉两个真缺陷：
1. **行类型判定不该依赖 CNN**：预处理改变笔画后 CNN 会把整页判成歌词行 → 加了几何兜底
   （字高离散度 cv ≤ 0.18 且间距规整度 ≥ 0.45 判为谱行）。
2. `warnings` 在兜底分支里被提前引用（潜在 NameError），已修。


## 想清楚了 easytr 为什么行（关键，之前绕远了）

它的 `templates.npy` 是 **(1009, 30)**：1009 个原型，是**为这类谱（同一批出版物、2–3 种字体）定制**的，
识别时在**原生尺寸**上做 1-NN。同字体/同字号/同栅格下，同一个数字的位图几乎完全重合，1-NN 命中率极高。
**它不是"通用识别"，是"见过这本谱的字体"。**

今天在原始 9 px 上验证了这一点：**同字形的簇内 IoU 是 0.94–1.00**——同一数字几乎像素级重合。
而我之前把字放大到 27 px 再和清晰渲染的 27 px 模板比，模糊 vs 清晰，必然错。这是根本错误。

### 因此正确做法是「语料级模板库」，不是每页现建

1. 把**整个语料**（39 个带标注的曲目文件夹、约 100 张图）的原生字形统一聚类，预期只有 10–20 个紧密簇；
2. 所有簇代表拼成一张图，**命名一次**（人看或 VLM 看），得到覆盖全部曲目的模板库
   —— 等价于 easytr 的 1009 原型，但用**你的数据、你的字体**建，可解释、可增补；
3. 之后每页只做原生尺寸 1-NN（毫秒级）；出现新字体就多一个簇，确认一次即可。

这条路确定性、离线、可增量、跨曲目复用，而且正是 easytr 有效的原因。

## 已经确定的判断

1. **9 px 这一档，"逐字 + 通用模型"不可靠**（我的 CNN、MNIST、EasyOCR 逐字都试过）。
2. **同字体下"原生尺寸 + 模板 1-NN"可靠**（簇内 IoU 0.94–1.00）——这就是 easytr 的机制。
3. **VLM 整行在小尺寸裁剪下也可靠**（6123 循环 18/18），可作交叉校验。
3. **几何/符号（八度点、升降号、小节线、粘连拆分）必须由传统检测提供**——VLM 会丢 `#`，EasyOCR 不给逐字框。
